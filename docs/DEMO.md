# Five-minute technical demonstration

Audience: a technical professor/reviewer. Goal: demonstrate actual engineering boundaries and reproducible evidence in five minutes, without portraying fixtures as live tracking or exposing credentials. This is the current Phase 7 script; earlier Phase 4 limitations are superseded by implemented pairing and approved uploads.

## Prepare before the clock starts

Follow [SETUP.md](SETUP.md). Run the checks, build/reload `apps/extension/dist`, and start `npm run dev`. In a second terminal start `npm run dev:fixtures` at `http://127.0.0.1:4174`. Keep the six documentation tabs you need ready. Sign in without displaying passwords, personal history, `.env`, cookies or pairing codes on a recorded screen. Prefer a new intentionally created demo account; do not delete or alter an existing account to make the UI look empty.

Run `npm run test:browser-sync` beforehand. It starts actual Chrome/Express/Vite/PostgreSQL test flows with isolated test users, records screenshots/results in `.browser-smoke/`, cleans up, and verifies unchanged application counts. These are controlled test artifacts, not activity from a real person's browser. Do not open copied ephemeral extension folders from this harness; their profiles may already be cleaned up. Load the stable `apps/extension/dist` build.

## Optional live synchronization variation

If the account owner explicitly wants a live upload demonstration, replace the recorded-flow segment with Settings pairing and a scan of a normal public HTTP(S) website. Show the hostname and exact payload; approve only that scan. Do not promise tracker counts or a score in advance: real website/consent states change. A score-withheld scan cannot be synchronized. The IP-based local fixture is intentionally rejected for upload; do not change validation to bypass that safeguard. Use the isolated native workflow for a fully reproducible synchronized fixture instead.

After upload, refresh Overview/History, inspect saved methodology/coverage, and show Settings revocation. Comparison needs scans for at least two approved hostnames; if absent, explain its honest empty state rather than seeding fake production history. Removing a local connection alone does not revoke its server credential. Pairing codes and credentials must not appear in public screenshots or source.

## Failure and follow-up plan

If the API is unavailable, demonstrate local scanning and show the safe connection error. Do not say an upload succeeded. If the database is unavailable, readiness should return 503; stop the storage portion and show only already executed test evidence with its date/scope. On a restricted Chrome page, the popup should explain that it cannot scan. If a check fails, show the actual failure and affected boundary rather than re-labeling it as a successful demo.

Be ready to discuss: why resource references differ from behavior, first-party CNAME/proxy blind spots, source licensing, synthetic-label bias, legacy score provenance, device revocation/ownership, in-process rate limits, and why backup/restore/TLS acceptance cannot be claimed from local unit tests.
